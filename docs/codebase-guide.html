MAP

What happens to one question

Before any single file makes sense, hold this shape in your head. A question enters, five graph nodes act on it in turn, and a schema-checked JSON object comes out. Every file in the project is a piece of this path or a way of measuring it.

agent.py · 5 nodes, 2 conditional edges · every path ends at finalize

Two decisions in that picture are the whole design. The first conditional edge means a prompt-injection attempt never reaches your retrieval code at all — it is refused in the first node. The second conditional edge is the tool router: it decides whether this is a policy question (go to the knowledge base) or an application question (go to the dataset). And finalize is a single choke point, so there is exactly one place where an answer can be refused and exactly one place where a response is checked against the schema.

01

Foundations

Four files with no interesting dependencies of their own. Everything else imports them. Read these first and the rest of the project stops containing surprises.

config.py 67 lines shared

One place where every path, tuning number and mode flag lives.

There are no magic numbers scattered through this project. Chunk sizes, the collection names, the top-k value, the file locations and the refusal threshold are all defined here and imported everywhere else. Change FIXED_CHUNK_SIZE here and the indexer, the evaluator and the agent all move together.

The last few lines create the output directories on import, which is why you can clone the repo with no logs/ folder and the first run still works.

The one number to understand

# NOT a tutorial preset. Measured by calibrate_threshold.py
#   sentence collection: in-scope 0.6930..0.8142 | out 0.1451..0.1932
#   fixed collection   : in-scope 0.6230..0.7816 | out 0.1424..0.1979
GROUNDEDNESS_THRESHOLD = 0.4104

def mock_llm_enabled() -> bool:
    """True unless the operator explicitly opts into a real LLM."""
    return os.getenv("MOCK_LLM", "1").strip().lower() not in ("0", "false", "no")
Why it's built this way

The default is "1", so mock mode is what you get unless you deliberately opt out. That single line is what makes "runs with zero API keys" true rather than aspirational — you cannot accidentally require a key.

dataset.py 212 lines Task 1

Invents 48 fake job applications, the same 48 every single time.

This is a seeded generator. random.Random(20260828) creates a private random number stream, so the "random" salaries and ages are identical on your machine and your grader's. Nothing here touches the global random module, which means importing this file cannot disturb randomness anywhere else.

The trick that guarantees coverage

The brief demands every category appears at least 3 times and every status at least once. Drawing 48 random categories would probably satisfy that, but "probably" is not a guarantee. So instead the code builds a pool with exact counts and shuffles it: 

category_pool = []
for cat, n in CATEGORY_QUOTA.items():   # {"Software Engineer": 12, ...}
    category_pool.extend([cat] * n)      # exactly 12 of them, etc.
rng.shuffle(category_pool)               # order is random, counts are not

Only flagged_priority_review is left to chance — a coin flip at p = 0.20 — because the brief wants that percentage to land in a band (10–30%) rather than hit an exact number. It comes out at 7/48 = 14.58%.

The helper that matters later

def days_percentile(p: float) -> float:
    values = sorted(r["days_since_created"] for r in JOB_APPLICATIONS)
    k = (len(values) - 1) * (p / 100.0)
    lo, hi = int(k), min(int(k) + 1, len(values) - 1)
    return values[lo] + (values[hi] - values[lo]) * (k - lo)  # interpolate
Why it's built this way

days_percentile(80) returns 23.0, and that number becomes the divisor in the escalation formula in tools.py. This is how a "designed" score differs from an invented one — the constant is read out of the data rather than picked because it looked round.

embeddings.py 53 lines shared

Turns text into 384 numbers, using one model loaded once.

An embedding is a list of numbers that represents meaning. Sentences about probation land near each other in that 384-dimensional space; a sentence about biryani lands far away. That is the entire basis of retrieval in this project.

The model is loaded lazily inside get_model() and cached in a module-level variable. Loading MiniLM takes about 20 seconds, so doing it once per process instead of once per call is the difference between the demos taking 20 seconds and 20 minutes. 

def embed(texts, normalize=True) -> np.ndarray:
    return get_model().encode(list(texts), convert_to_numpy=True,
                              normalize_embeddings=normalize)
Why it's built this way

normalize_embeddings=True scales every vector to length 1. Once vectors are unit-length, cosine similarity is just the dot product — so elsewhere in the code you will see bare a @ b and mat @ q doing similarity work with no division. That is why those lines are so short.

llm.py 268 lines MOCK_LLM

The only place the project talks to a "language model" — and the mock that stands in for one.

This is the most conceptually interesting file in the repo. It defines one interface with two implementations. get_llm() hands back MockLLM by default and RealLLM only if you explicitly set MOCK_LLM=0. Nothing else in the codebase knows or cares which one it got.

How the mock answers a question

It cannot generate text, so it selects text. Given the question and the retrieved chunks, it splits the chunks into sentences, scores each sentence against the question, and returns the best three in their original reading order: 

q   = np.asarray(embed_one(question))
mat = embed(sentences)
scored = sorted(((float(np.dot(q, mat[i])), sentences[i])
                 for i in range(len(sentences))), key=lambda t: -t[0])

picked = [s for sc, s in scored[:3] if sc >= SENTENCE_FLOOR]
picked.sort(key=sentences.index)   # restore reading order
return " ".join(picked)
The elegant part

Because it can only return sentences that are physically present in the retrieved context, this mock cannot hallucinate. Not "is unlikely to" — cannot, structurally. That is a genuinely stronger groundedness guarantee than a real LLM gives you, and it is why the whole project is honest under mock mode.

How the mock judges an answer

judge_triad() scores three things a human evaluator would look at: did we retrieve relevant context, is every claim supported, and does the answer address the question. Refusals get special handling, because a refusal is a different kind of object from an answer: 

REFUSAL_PREFIXES = ("i don't know", "i can't act on that")

if refusal:
    groundedness     = 1.0                      # asserts nothing → nothing unsupported
    answer_relevance = 1.0 - context_relevance  # right call iff context was empty
Why it's built this way

That second line is doing real work. If the agent refuses when there was good context, context_relevance is high, so answer relevance scores near zero and the metric punishes it. An over-cautious agent that refuses everything would look bad in the numbers, which is exactly what you want an evaluation to do.

02

Retrieval

Turning twelve policy documents into something searchable, then proving the search actually works and choosing a refusal threshold from measurement rather than habit.

rag_core.py 350 lines Tasks 2–4

Chops documents two different ways, stores both in a vector database, and answers questions from what it finds.

Step 1 — chunking

You cannot embed a whole document usefully; the meaning gets averaged into mush. So documents are cut into chunks. This project implements two strategies so it can compare them: 

def chunk_fixed_overlap(text, size=420, overlap=90):
    step = size - overlap            # slide 330 chars at a time
    for start in range(0, len(text), step):
        chunks.append(text[start:start + size])   # blind character window

def chunk_sentences(text, group=2, stride=1):
    sents = split_sentences(text)
    for start in range(0, len(sents), stride):
        chunks.append(" ".join(sents[start:start + group]))  # whole sentences

The first cuts at character 420 regardless of what is there — often mid-sentence. The second always ends on a sentence boundary, and consecutive windows share a sentence so a rule spanning two sentences is never split. Fixed gives 24 chunks; sentence gives 36.

Step 2 — indexing

Each strategy gets its own ChromaDB collection. Metadata on every chunk records which parent document it came from, which is what makes document-level scoring possible later. 

coll = client.create_collection(name=coll_name,
    metadata={"hnsw:space": "cosine", "strategy": label})
coll.add(ids=ids, documents=texts, metadatas=metas,
         embeddings=[v.tolist() for v in vectors])

Step 3 — retrieval

res = coll.query(query_embeddings=[qvec], n_results=k)
# Chroma returns DISTANCE; convert to similarity so bigger = better
similarity = round(1.0 - float(dist), 4)
Easy to get wrong

Chroma gives you cosine distance, where 0 means identical. Every threshold in this project is expressed as a similarity, where 1 means identical. Forget the 1.0 - dist conversion and every comparison in the codebase silently inverts.

Step 4 — grounded answering

if not hits or top_sim < threshold:
    return RagResult(answer=FALLBACK_ANSWER, grounded=False, ...)
answer = get_llm().generate_grounded(query, contexts)

The check comes before generation. If nothing relevant was retrieved, the model is never asked, because there is no context for it to be honest with.

calibrate_threshold.py 91 lines Task 4

Measures where "I don't know" should kick in, instead of guessing.

The brief specifically forbids picking 0.5 or 0.7 off a tutorial. So this script asks the index six questions it can answer and three it cannot, records the top similarity for each, and looks at the gap between the two clusters.

CollectionIn-scopeOut-of-scopeGapMidpoint
sentence0.6930 – 0.81420.1451 – 0.19320.49980.4431
fixed0.6230 – 0.78160.1424 – 0.19790.42510.4104
What the measurement revealed

The clusters are separated by roughly half a point of cosine similarity. The popular defaults — 0.5, 0.6, 0.7 — all sit inside the in-scope cluster, meaning they would reject real, answerable questions. Guessing would have quietly broken the agent in a way that still looked fine on a happy-path demo.

The lower of the two midpoints is taken so one threshold is safe for either collection.

eval_chunking.py 179 lines Task 5

Scores both chunking strategies against hand-labelled correct answers.

GOLD is a hand-written list: for each of five questions, which knowledge-base documents genuinely answer it. Then for each collection, the top-3 chunks are mapped back to their parent documents, de-duplicated, and compared against that gold set. 

R = de-duplicated retrieved parent documents
G = hand-labelled relevant documents

Precision@3 = |R ∩ G| / |R|    # of what I showed, how much was right
Recall@3    = |R ∩ G| / |G|    # of what was right, how much did I show

Using |R| rather than a hard 3 is a deliberate choice, explained in the file's docstring: after de-duplication, three chunks of the same correct document is one document surfaced, and dividing that by 3 would punish the strategy for being consistent.

The result is not a clean win

Sentence-based wins precision (0.80 vs 0.63); fixed-size wins recall (1.00 vs 0.80). The recommendation argues that fixed-size only reaches perfect recall because its wide windows sweep in extra documents indiscriminately — the same behaviour that costs it precision. Worth reading as an example of defending a choice when the numbers do not simply hand it to you.

03

The agent

Five files that turn retrieval into something that can be called an agent: a second tool, a contract for its output, three guardrails, a memory, and the graph that wires them together.

tools.py 181 lines Task 6

Looks up one application and scores how urgently a human should look at it.

The lookup itself is a dictionary read. The interesting part is the escalation score, which had to be designed rather than being a boolean OR of the two signals: 

recency_norm     = min(days_since_created / 23.0, 1.0)
escalation_score = 0.60 * flagged_priority_review + 0.40 * recency_norm
SituationScoreEscalates at 0.40?
Flagged, any age0.60 – 1.00yes, on the flag alone
Unflagged, 23+ days old0.40yes, exactly at the line
Unflagged, 13.5 days (median)0.235no
Unflagged, brand new0.00no
Where 23.0 comes from

It is the 80th percentile of days_since_created in the generated data. So the threshold of 0.40 reads, in plain English: escalate everything a recruiter already flagged, plus the slowest-moving fifth of everything else. Both the divisor and the threshold are traceable to the dataset instead of chosen for looking tidy.

schemas.py 115 lines Task 9

Declares the exact shape of every response, and refuses to let a malformed one out.

A JSON Schema listing required keys and their types. additionalProperties: false means an unexpected key is an error, not something quietly tolerated. Validation runs inside finalize on every single response. 

"trace_id": {"type": "string", "minLength": 8},
"route":    {"enum": ["rag", "record_lookup", "blocked"]},
"escalation": {"type": ["object", "null"], ...}
It caught a real bug while I was building this

The triad evaluator originally passed trace_id="eval-01" — seven characters. The schema's minLength: 8 rejected it, and all 15 queries came back as the blocked error envelope. The schema was not decoration; it stopped bad output from escaping and made the cause obvious. That is what enforcement looks like when it is doing its job.

guardrails.py 254 lines Task 10

Three independent safety checks: two on the way in, one on the way out.

1 · PII masking

PHONE_RE = re.compile(r"""(?<![\w])(
        (?:\+91[\-\s]?|0)?     # optional +91 or 0 prefix
        [6-9]\d{4}             # Indian mobiles start 6-9
        [\-\s]?\d{5}
    )(?![\w])""", re.VERBOSE)

The lookarounds (?<![\w]) and (?![\w]) are the important part. Without them the pattern would happily chew into NAU-1003 or a salary like 2970000. The demo deliberately includes a test case proving both survive untouched.

2 · Prompt-injection detection

Nine regex patterns, each paired with a human-readable reason so the log says why something was blocked rather than just that it was — instruction override, system-prompt exfiltration, persona override, guardrail disabling, and so on.

3 · Groundedness, in two stages

# stage 1 - was anything relevant even retrieved?
if top_similarity < threshold:
    return GroundednessVerdict(False, ...)

# stage 2 - is every SENTENCE of the answer traceable to context?
sims = embed(ans_sents) @ embed(ctx_sents).T
unsupported = [s for i, s in enumerate(ans_sents) if sims.max(axis=1)[i] < 0.60]
Why two stages

Stage 1 catches the out-of-scope question — nothing relevant exists, so refuse. Stage 2 catches something subtler: retrieval was good but the answer contains an invented claim. The demo proves it by feeding in a fabricated sentence about a "two lakh rupee relocation bonus" alongside a genuine one; stage 2 flags exactly the fabricated sentence. Stage 2 is the check that would matter most if you swapped the mock for a real LLM.

memory.py 139 lines Task 8

Remembers a conversation in a JSON file that outlives the process.

Two things are stored per conversation: turns, an append-only history, and facts, a small dictionary of things worth recalling. facts is what makes multi-turn behaviour visible. 

{"conv-alpha": {
   "turns": [ {"turn_index": 1, "role": "user", "text": "..."}, ... ],
   "facts": {"last_record_id": "NAU-1003"}
}}

Every write takes a threading.Lock and rewrites the whole file. That is crude and would not scale, but it is correct under the concurrent requests FastAPI can produce, and correctness at this size is the right trade.

How the demo proves memory actually works

The same sentence — "And what is the escalation score for it?" — is run twice. With history, "it" resolves to NAU-1003 from facts.last_record_id. In a fresh conversation the identical sentence has nothing to resolve against, falls through to the RAG route, and is correctly refused. Same input, different state, different behaviour: that is the proof, and it is much stronger than just showing that memory was written.

agent.py 569 lines Task 7 · the core

The LangGraph graph — five nodes, two conditional edges, one entry point.

State

LangGraph passes a single dictionary between nodes. Declaring it as a TypedDict with total=False means every key is optional, so each node returns only the keys it changed and LangGraph merges them in. 

class AgentState(TypedDict, total=False):
    query: str
    masked_query: str
    route: str                # "rag" | "record_lookup" | "blocked"
    contexts: List[str]
    executed_nodes: List[str] # breadcrumb trail, used by the checkpoint demo

Nodes are plain functions

There is nothing framework-ish about them. Each takes state and returns a partial dict: 

def guard_input(state):
    masked, pii_fired, _ = mask_pii(state["query"])
    injected, reasons = detect_injection(masked)
    return {"masked_query": masked, "pii_masked": pii_fired,
            "injection_detected": injected}

Edges are also plain functions

A conditional edge is a function returning a string, plus a mapping from string to node: 

def after_route(state):
    return state["route"]         # "rag" or "record_lookup"

g.add_conditional_edges("route_intent", after_route,
                        {"rag": "rag_answer", "record_lookup": "record_lookup"})

How routing actually decides

Three rules, in order: an explicit NAU-1234 in the text wins; otherwise a referring phrase ("for it", "that one") plus a lookup keyword plus a remembered record id resolves from memory; otherwise it is a policy question.

Why all three conditions are required together

Requiring the referring phrase and a lookup keyword and a stored id is what stops turn 3 of the demo ("How long is the probation period?") from being dragged back to the record-lookup branch just because a record was discussed earlier. Memory should be available, not sticky.

finalize is the choke point

Every path ends here, and it does four things in order: run the groundedness guardrail (rag route only), assemble the response, validate against the schema, and persist the turn. If validation fails, the response is replaced — not patched — with a conformant error envelope: 

ok, msg = validate_agent_response(response)
if not ok:
    response = { "route": "blocked",
                 "answer": "...did not conform to its output schema...", ... }

Serving

Putting the agent behind HTTP, and recording what happened without leaking anything.

structured_logging.py 101 lines Task 12

Writes one JSON line per request, with the phone number already removed.

JSON Lines means one complete JSON object per line — greppable with ordinary tools, streamable, and appendable without rewriting the file. Each entry carries a trace_id and latency_ms. 

def log_request(*, trace_id, endpoint, request_text, ...):
    safe_text, pii_masked, _raw = mask_pii(request_text or "")
    # ^ masked HERE, unconditionally, even if the caller already masked
Why mask twice

The agent already masks before the model sees anything. Masking again at the moment of writing means there is no code path — no future endpoint, no forgotten caller — that can put a raw phone number on disk. Defence at the boundary rather than trust in callers. The demo greps the finished log file to prove it.

Four HTTP endpoints, with request and response shapes enforced by Pydantic.

Pydantic models do validation for free — min_length=1 on the query means an empty request is rejected with HTTP 422 before your code runs. The demo drives everything through TestClient, which exercises the real ASGI app and real routes without needing a server process.

The demo adds a travel-reimbursement policy and then immediately asks a question about travel expenses — and gets a grounded answer citing the document that did not exist a second earlier.

05

Judging

Measuring the finished agent across a test set designed to cover everything it should know and several things it should refuse.

eval_rag_triad.py 193 lines Task 13

Scores 15 questions on three axes using an LLM-as-judge prompt.

The test set is deliberately constructed: twelve questions, one per knowledge-base topic, plus two out-of-scope questions and one prompt injection. The three axes are the standard "RAG triad":

AxisQuestion it answersAverage
Context relevanceDid retrieval find the right material?0.5956
GroundednessIs every claim backed by that material?1.0000
Answer relevanceDoes the answer address the question?0.7511
Read this number carefully

Context relevance of 0.5956 looks mediocre until you split it: the twelve in-scope questions average 0.7210, while the three out-of-scope ones average 0.0939 and drag the mean down. That low score is the system working — there genuinely is no relevant context for a biryani recipe, and the agent refused instead of inventing one. An aggregate metric that you cannot decompose will mislead you; always look at the breakdown.

06

Hardening

The parts that separate a demo from something you could put in front of real recruiters: standard interfaces, surviving interruption, and failing fast instead of hanging.

mcp_server.py · mcp_client.py 58 + 134 lines Task 14

Publishes the lookup tool over a standard protocol so anything can call it.

MCP (Model Context Protocol) is a standard way to expose tools to AI systems. Wrapping the function takes one decorator — and the docstring is not decoration, it becomes the tool description other systems read to decide when to call it. 

@mcp.tool
def check_job_application_status(record_id: str) -> Dict:
    """Look up the status of a Naukri.com job application by its record id.
    Args:
        record_id: The application identifier, for example "NAU-1003".
    """
    return _lookup(record_id)
The mistake that costs an hour

fastmcp's HTTP transport mounts at /mcp, not at the bare root. Point a client at http://127.0.0.1:8765 and you get a 404 with no useful hint; it must be http://127.0.0.1:8765/mcp. Also: the package is fastmcp, no hyphen — fast-mcp is a different, unrelated project.

The client is a separate file run as a separate process, which is the point: it proves the tool is reachable across a real process boundary rather than just being importable.

checkpoint_demo.py 275 lines Task 15

Stops a run halfway, then finishes it in a completely different process.

LangGraph can save its state to SQLite after every node. Attach a checkpointer, give the run a thread id, and an interrupted run can be resumed later: 

with SqliteSaver.from_conn_string(str(CHECKPOINT_DB)) as saver:
    graph  = build_graph(saver, interrupt_before=["rag_answer"])
    config = {"configurable": {"thread_id": THREAD_ID}}
    graph.invoke(state, config=config)   # runs 2 nodes, then stops
    # ... later, elsewhere ...
    graph.invoke(None, config=config)    # None = "resume, don't restart"
How it proves nodes weren't re-run

Each node is wrapped in a counter that records executions in this process. The two phases run as separate OS processes, so process B starts with an empty counter. After resuming, its counter reads ['rag_answer', 'finalize'] — yet the final state contains all four nodes. The first two were loaded from SQLite, not recomputed. Running it in one process would have proved much less, since anything could have been left in memory.

resilience_demo.py 431 lines Task 16

Retries flaky calls, and refuses to hang when something takes too long.

Retries with exponential backoff

RETRY_POLICY = RetryPolicy(
    max_attempts=4, initial_interval=0.25, backoff_factor=2.0,
    max_interval=2.0, jitter=True,
    retry_on=(TransientToolError,),   # NOT bare Exception
)

Waits grow 0.25s → 0.5s → 1.0s, so a struggling service gets increasing breathing room. Jitter adds randomness so that a thousand clients retrying do not all hit at the same instant. Naming a specific exception in retry_on matters: with bare Exception, a genuine bug would be retried four times and take four times as long to surface.

Timeouts

pool = ThreadPoolExecutor(max_workers=1)
try:
    return pool.submit(fn, state).result(timeout=timeout_s)
except FutureTimeout:
    raise NodeTimeout(...)
finally:
    pool.shutdown(wait=False)   # do NOT wait for the doomed worker
A bug I hit building this — worth internalising

The first version used with ThreadPoolExecutor(...) as pool:. That reads naturally, but the context manager's exit calls shutdown(wait=True), which blocks until the worker finishes. The timeout fired correctly at 1 second and then the caller sat there for the full 5 seconds anyway — reintroducing the exact hang the timeout existed to prevent. The test caught it because it asserts on elapsed time, not just on the exception type. Assert on the property you actually care about.

The global timeout uses two mechanisms together: an outer bound that releases the caller at the deadline, and a shared Deadline object every node checks on entry so the run genuinely stops advancing. Both are needed, because Python cannot forcibly kill a running thread.

run_all.py 165 lines tooling

Runs every demo as its own subprocess and saves the output.

Each step runs isolated, so one crash cannot corrupt another's state, and output is filtered of model-loading noise before being written to transcripts/.

One ordering detail worth noticing

The API demo adds a thirteenth document via /add-document. If the triad evaluation ran after that, it would score a different knowledge base than the one documented. So there is an explicit re-index step between them. Evaluation has to score a known, fixed corpus or the numbers mean nothing.

Regenerate a single transcript instead of all sixteen:

python run_all.py 13   # only the RAG triad step
REF

Concepts glossary

Every term in this codebase that is worth being able to define out loud.

Embedding
A list of numbers representing a piece of text's meaning. Here, 384 of them per chunk, produced by all-MiniLM-L6-v2.
Cosine similarity
How close two embeddings point in the same direction. 1.0 is identical, 0 is unrelated. On unit-length vectors it is just the dot product.
Chunking
Splitting documents into retrievable pieces. Too big and meaning is diluted; too small and context is lost.
Vector store
A database that finds the nearest embeddings to a query embedding. ChromaDB here, one collection per chunking strategy.
RAG
Retrieval-Augmented Generation: retrieve relevant text first, then answer using only that text.
Grounding
Every claim in an answer traceable to retrieved source text. The opposite of hallucination.
Top-k
How many chunks to retrieve per query. This project uses 3.
Precision / Recall
Precision: of what you returned, how much was right. Recall: of what was right, how much you returned. They trade off against each other.
Graph state
The dictionary LangGraph passes from node to node. Each node returns only the keys it changed.
Conditional edge
An edge whose destination is decided at runtime by a function returning a route name.
Checkpointer
Storage that saves graph state after each node, so an interrupted run can resume where it stopped.
Thread id
The key a checkpointed conversation is stored under. Same id means same conversation.
MCP
Model Context Protocol — a standard interface for exposing tools to AI systems.
Exponential backoff
Doubling the wait between retries, so a failing service is not hammered.
Jitter
Randomness added to backoff so many clients do not retry in lockstep.
Prompt injection
Input crafted to override an agent's instructions. Blocked here before it reaches retrieval.
JSON Lines
One JSON object per line. Appendable, streamable, greppable with ordinary tools.
LLM-as-judge
Using a model to score another model's output on defined axes rather than checking exact strings.
